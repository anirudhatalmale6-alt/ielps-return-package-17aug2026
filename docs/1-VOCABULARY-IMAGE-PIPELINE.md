# 1 — A1–C2 vocabulary image pipeline

Return package item 1. Specification. Nothing here has been built or deployed;
it is the design your instruction asks for, written so it can be implemented
exactly once and reused by Studio/CLAIS.

---

## Read this first

Your instruction approves "images currently generated by the server" for
temporary use. **The server does not generate vocabulary images.**

`lesson_engine_15.js` emits `visualDefinition` and `imageExample` as *sentences
describing a picture that should be drawn* — image **briefs**, not image
locations. There is no image generation call anywhere in the backend, no image
generation queue, no stored generated asset, and no field that ever holds an
image URL for a vocabulary word.

So the temporary approval, as written, applies to an empty set. It costs
nothing and blocks nothing — but it should not be recorded as "temporary
vocabulary images are live", because none are. The full count is in item 2:
**6 of 648 unique A1–C2 keywords have a picture; 642 have none.**

The pipeline below is therefore specified as the thing that will *create* the
library, with the temporary-use rule built in for when generation starts.

---

## The learner-facing rule

The complete rule from your instruction, which the pipeline exists to satisfy:

```
Keyword → meaning/definition → clear graded example sentence using that
keyword in context, appropriate to the learner's CEFR level → AI-generated image
```

Two of those four are not yet met by the platform. See item 2 for the evidence.

---

## Permanent architecture

```
server image brief + vocabulary item + definition + CEFR-graded contextual
example sentence
      ↓
AI image generation
      ↓
A1–C2 vocabulary asset pipeline
      ↓
review / approval
      ↓
Studio / CLAIS / content publishing
      ↓
permanent IELPS vocabulary asset
      ↓
vocabulary card
```

### Stage 1 — semantic authoring specification (exists today)

`GET /api/lesson-support/lessons/:id/image-briefs` already returns, per lesson,
the `imageBriefs` and, per word, `visualDefinition` and `imageExample`. Your
instruction designates these the semantic authoring specification for the image
component, and that is what the pipeline consumes. Nothing about that route
needs to change to start.

One correction it *does* need before the briefs are usable at scale: the brief
text interpolates `unit.focus` verbatim, and `unit.focus` is often a
comma-separated list. So A1 unit 1 currently produces

> "Show hello clearly in a greetings, names, classroom instructions situation…"

which is not a usable prompt. The fix is small and belongs to whoever
implements generation; I have not made it, because it changes learner-visible
generated text.

### Stage 2 — generation

One image per **unique keyword per CEFR level**, not per lesson occurrence. A
word that appears in four B1 lessons gets one B1 picture; the same word at A1
and B1 may legitimately get two, because the depiction should suit the level.

Input to the generator: keyword, definition, the CEFR-graded example sentence,
the image brief, the CEFR level, and the unit focus as context.

Non-negotiables carried from your instruction, to be enforced in the generator
prompt and in review:

- No unrelated stock photography, no decorative filler, no generic level
  illustrations used merely to fill a slot.
- Abstract vocabulary — *please*, *politely*, *repeat*, *again* — is illustrated
  by its **communicative meaning or context**, never by forcing a literal
  object. A picture of a mouth for "repeat" teaches nothing; two people, one
  saying something again while the other listens, teaches the function.
- No brand marks, no embedded answer text, culturally neutral, accessible
  contrast.

### Stage 3 — batching into six libraries

Every generated image is filed into exactly one of:

```
A1 Vocabulary Image Library
A2 Vocabulary Image Library
B1 Vocabulary Image Library
B2 Vocabulary Image Library
C1 Vocabulary Image Library
C2 Vocabulary Image Library
```

Proposed on-disk layout, matching the convention `content-assets/` already uses
for lesson illustrations (`images/lesson-illustrations/<level>/<unit>/<lesson>.*`):

```
content-assets/vocabulary-images/<level>/<keyword-slug>.<ext>
```

`<keyword-slug>` is the lowercase keyword with non-alphanumerics collapsed to
hyphens. Flat within a level, because the asset belongs to the **word at that
level**, not to a single lesson — the same picture is correctly reused by every
lesson at that level that teaches the word.

Nothing is left as an unstructured collection: the inventory in item 2 is the
index, and an asset that is not in it does not exist as far as the platform is
concerned.

### Stage 4 — review

Review states:

```
TEMPORARY_UNREVIEWED → REVIEW_REQUIRED → APPROVED → PUBLISHED
                                       ↘ REJECTED → REGENERATE → (back to review)
```

- **TEMPORARY_UNREVIEWED** — generated and shown to learners under your
  temporary display permission. Displayable, not approved.
- **REVIEW_REQUIRED** — awaiting editorial judgement. Also the state of a word
  that has no image yet, so the queue and the gap list are the same list.
- **APPROVED** — editorially accepted; ready to be promoted.
- **REJECTED** — accepted as wrong. Not displayed.
- **REGENERATE** — rejected with a reason that should feed a new generation.
- **PUBLISHED** — promoted into the permanent IELPS content asset library and
  referenced by `permanentAssetReference`.

**Temporary display permission is not permanent content approval.** Only
`PUBLISHED` assets are permanent IELPS content.

### Stage 5 — permanent publishing

Promotion from `APPROVED` to `PUBLISHED` copies the asset to its permanent
location and writes `permanentAssetReference`. A published asset is immutable —
a change means a new asset and a new reference, so a lesson that was reviewed
cannot silently change under a learner.

## Required traceability metadata

Every row carries the full chain from your instruction:

```
CEFR level → course/unit/module → lessonId → keyword → definition →
graded example sentence → image brief → generated image → review status →
permanent asset reference
```

Implemented as the inventory columns in item 2, which already exist and are
populated for all 2,880 keyword occurrences:

| Column | Source today |
| --- | --- |
| `cefrLevel` | curriculum |
| `unitId`, `unitFocus` | curriculum |
| `lessonId`, `lessonTitle` | curriculum |
| `keyword` | curriculum `vocabularySet` |
| `definition` | `CEFR_STYLE.definitionFrame` — **template, not authored** |
| `gradedExampleSentence` | `CEFR_STYLE.exampleFrame` — **template, not authored** |
| `imageBrief` | `visualDefinition` |
| `generationBrief` | `imageExample` |
| `generatedImage` | empty for 642 of 648 unique keywords |
| `imageState` | `PRESENT` / `MISSING` |
| `reviewStatus` | `TEMPORARY_UNREVIEWED` / `REVIEW_REQUIRED` |
| `permanentAssetReference` | empty — nothing is published yet |

## The image-pending state — already built

Your instruction: *"If no image exists yet, retain Keyword →
meaning/definition → graded example sentence and show a clean image-pending
state."*

That is already how the approved keyword pop-up behaves. `resolveKeywordImage()`
tries, in order: an image the lesson genuinely supplied; an IELPS illustration
drawn for that exact word; and otherwise returns a `brief` state, which renders
as "No picture supplied for this word yet" above the word's own visual brief —
with the keyword, meaning and example still shown in full.

There is deliberately no decorative fallback, for the reason your instruction
gives: a picture that merely fills the slot teaches the wrong meaning. Nothing
needs changing here.

## Exposing the pipeline to Studio / CLAIS

Your instruction asks that future authored courses use the same system. The
smallest honest way to do that, without duplicating backend routes:

- Studio consumes the **existing** `/api/lesson-support/lessons/:id/image-briefs`
  as its authoring specification, rather than growing its own brief format.
- Generation, review-state transitions and publishing are one service used by
  both the A1–C2 backfill and Studio authoring — not a second implementation
  behind a Studio-specific route.
- Studio's authoring UI writes review-state transitions through that same
  service, so a Studio-authored word and a curriculum word are indistinguishable
  once published.

This is a design position, not built work. It needs your approval and a scope
before anything is written, and it is materially larger than the rest of this
package.

---

## Honest scope note

The four-part learner rule cannot be met by generating images alone. Two of the
four parts — the definition and the graded example sentence — are currently
machine-templated rather than authored, and the template *mentions* the keyword
rather than *using* it. Evidence and examples are in item 2. Generating 642
images on top of an unauthored example sentence would produce a library that
looks complete and still fails the rule you have written.

That decision is yours, and it is the one I would want made before generation
starts.
